# 「固定费用 + 返佣」混合收款结构（fixed + revshare hybrid）

> **来源**：[Lxcardoza993/awesome-oss-sponsorship](https://github.com/Lxcardoza993/awesome-oss-sponsorship)（CC-BY-4.0），2026-09-02 由 Kit 提取整理。核心素材为该仓库 `README.zh-CN.md` 的「人民币怎么报价 + 固定+返佣怎么设计」章节与 `data/sponsor-types.yml` 的 `deal_models` 清单。
>
> **本文档怎么用**：原文场景是「开源仓库维护者与赞助商的合作收费」。本文档把该模式作为一种**收款结构选项**整理给 Justin（LegalAgent，负责团队合同与收款结构设计），与现有「分期付款」思路并列备用。未标注的部分是原文整理；标注「**迁移演绎**」的部分是结合本项目职责的场景改写。所有比例、区间均为**经验估算、仅供参考**，签约前以双方实际约定为准。

## 一、模式定义

**「固定费用 + 返佣」混合**：向合作方收取一个较低的固定合作费（保底），另加通过我方专属链接/口令转化的用户按约定比例返佣（上不封顶的分成腿）。

原文的一句话合同表述模板（可直接改造进协议）：

> 「¥[X]/月固定合作费，保证你的 logo/位曝光 + 基础流量；**外加**通过你的专属链接/口令转化的用户，按 [Y]% 返佣。双方按月对账，数字透明。」

在原文的交易模式全景（`deal_models`）里，它属于七种结构之一，且被原文标为「可预期性与上行收益的最佳平衡」：

| 结构 | 说明 | 特点 |
|---|---|---|
| 一次性（one_time） | 单笔付款买一个明确期限（一个版本、一个月） | 承诺最低 |
| 月付循环（monthly_recurring） | 可预期的月度收入 | GitHub Sponsors / Open Collective 档位的默认形态 |
| 年付（annual） | 约月价 8–10 倍，常见 15–20% 折扣 | 对方预算周期友好 |
| 纯返佣（affiliate_pure） | 0 固定费，纯按转化分成（10–30% 递归或一口价） | 纯绩效，收入全看转化 |
| 悬赏（bounty） | 按具体交付物（issue/PR）付固定赏金 | 一事一结 |
| **固定 + 返佣（fixed_plus_affiliate）** | **固定月费保底 + 转化分成** | **原文评价：可预期性 + 上行收益的最佳平衡** |
| 实物置换（in_kind） | 用服务/额度代替现金（托管、CI、监控） | 有真实价值，按公允价入账 |

## 二、为什么这个模式好（原文的双方分析）

- **对付款方**：**下行风险封顶**——固定费可控可预算，不担心花了钱没效果；转化好时自己也在赚钱，有动力继续。
- **对我方**：**保底现金流**兜住基本盘；转化好时获得**不对称收益**（分成腿不封顶）。
- **适合的谈判对象**（原文语境）：增长负责人（要绩效）、生态厂商（要曝光 + 转化）。

一句话：它把「双方对效果的不确定性」转换成了「双方分担、双方受益」的结构，因此比纯固定（对方怕亏）或纯返佣（我方怕白干）都更容易谈成。

## 三、设计要点（原文清单）

1. **固定费怎么定**：按对方「转化路径」的质量定——转化路径差（点过去也没法归因、没法注册）就**别加返佣腿，纯卖固定**；只有转化可归因时混合模式才成立。
2. **返佣比例**：国内常见 **10–30% 递归分成**，或 **¥X/注册** 的一口价。比例开多少取决于产品毛利和客户生命周期价值，签约前摸清对方定价。
3. **归因机制**：给对方一个**专属口令或专属链接**，让每一笔转化可追溯到这次合作——没有归因就没有对账基础，返佣腿形同虚设。
4. **对账周期**：按月对账，数字透明（原文模板里明写「双方按月对账」）。
5. **书面协议**：国内走对公转账必须签书面合作协议，至少约定——合作期限（term）、对账周期、最低保证（如有）、取消条款。
6. **收款渠道**：国内合作方走对公转账为主（国内 sponsor 常用人民币对公、微信、支付宝）；海外合作方走 Open Collective / GitHub Sponsors（注意：**GitHub Sponsors 不支持中国大陆**，香港/澳门特区可以——涉及海外收款时先核实通道）。

### 迁移演绎：适用的团队场景

该结构在团队内适用的服务类型——**成果可以量化归因到本次合作的服务**：

- 增长/引流类交付（Buzz 的渠道投放：固定投放费 + 带来转化的分成）；
- 转化优化类交付（Hopkins 的漏斗优化：基础服务费 + 成交额提成）；
- 分销/带货类合作（产品销售的渠道合作：坑位费 + 销售返佣，即国内常见的「坑位费 + 佣金」模式，与直播带货的「坑位费 + CPS」同构）。

不适用的场景（判断边界）：**成果无法归因到本次合作**的项目（如纯设计、一次性交付物、代写文档）——归因腿立不起来，强行写返佣条款只会带来对账纠纷；这类用固定费或分期付款结构。

### 迁移演绎：与「分期付款」的关系

分期付款（现有思路）解决的是**付款节奏**问题——把大额交付拆成多期降低对方资金压力；「固定 + 返佣」解决的是**风险分担**问题——把「效果不确定性」转化为双方共担。两者是不同维度的结构选项，可以叠加使用（如：固定腿本身分两期支付 + 转化分成按月结算）。Justin 设计时先判断核心矛盾是资金压力还是效果风险，再选结构。

## 四、条款清单（起草协议时的核对项）

起草这类协议时，至少逐项确认以下条款（原文要点 + 迁移演绎补充）：

- [ ] 固定费金额、支付节奏（月付/分期）、发票与对公账户信息
- [ ] 返佣比例或单价（递归还是一次性、递归持续多久）
- [ ] 归因机制（专属链接/口令；归因窗口多长——参考原文 affiliate 程序常见的 30/45/90 天 cookie 窗口）
- [ ] 对账周期与方式（每月几号、以哪方数据为准、数据争议怎么处理）
- [ ] 最低保证（保底量，如有）
- [ ] 合作期限、续约与取消条款（提前多久通知、已产生的返佣怎么结清）
- [ ] 数据透明义务（双方按月互见转化数据）
- [ ] 排他与否（合作期内是否限制接同类竞品合作）
- [ ] 争议解决与适用法律

## 五、纪律红线

- 返佣链接/口令必须**明示披露**，不得伪装成中立推荐（原文反复强调：一次坏推荐损失的可信度远超那点佣金）。
- 估算的转化预期永远标注「仅供参考」，不写进具有约束力的承诺条款。
- 只接愿意签书面协议的合作——口头约定的返佣没有对账基础，等于没有。
